## Disturbance model

```
wind     F = level^2 * 0.5*rho_air*CdA * |V_aw| * V_aw     V_aw = wind_enu - v_hull
current  F_body = level * drag_linear * (c_body - v_body)
waves    sum_i amp_n[i] * sin(2*pi*f_i*t + phase_i), random per-episode direction,
         level-linear; separate yaw moment sum with its own phases
```

`level = 0` is exactly zero because every term is multiplied by `level` or `level^2`
(asserted bit-exact, float32 and float64, 200 steps). `sample()` is algebraic in `(t,
state)`: no internal integration, so it cannot drift with `dt`; wave phases and wind
direction are drawn in `reset()` from a seeded `torch.Generator`
(`configs/disturbance.yaml:seed_offset`), which makes runs reproducible.

Current is modelled as a **relative-flow drag term**, not by shifting the whole drag model
into Fossen relative-velocity form. That is a documented simplification (`sim/disturbance.py`
docstring, marked TODO) and stays until A1's drag coefficients are identified.

## Sensor model

Per source, an accumulator fires on its own `rate_hz` epoch and the last sample is held
between epochs (`gps.hold_last`). GPS position goes through a rolling window of past true
positions (`latency_s`), so the fix is what the receiver computed earlier, not what is true
now; `gps_lat/lon` are always derived back from the noisy ENU fix via
`common.frames.enu_to_latlon`, so lat/lon, SOG and COG stay mutually consistent.

Heading fusion reproduces the structure of the Pi's `fusion.py`: gyro propagation every
step, mag-primary correction with the measured gain `mag_weight/(mag_weight+gyro_weight)
= 0.02` (`fusion.py:54`), snap on the first mag sample, plus a GPS-course pull only when
`sog >= gps_heading_min_speed_mps`. Position is low-passed with `gps_alpha` (`0.7`,
measured). `gps_valid` / `sensor_ok` come from sample age vs `stale_after_s`.

`(u, v)` come from `common/estimator.py`, so a lost fix decays the estimate first-order
instead of snapping it to zero.

`est` = `[pos_east_hat, pos_north_hat, psi_rad, u, v, r_rad]` — the CONTRACT §2 state
layout, built from estimator output only. `true_state` is used solely to synthesise the
measurements; the policy never sees it.

`common/estimator.py` has no imports, no `np.`/`torch.` call and no `isinstance` branch:
cos/sin are Chebyshev-fitted power series (max error 2.1e-11 rad on `[-pi, pi]`), which is
what lets the same source run in torch inside the sim and in numpy on the Pi. The gate is
written as arithmetic (`bool*1.0`), which behaves in both backends.

## OPEN ISSUES

1. **`enu_to_latlon` runs on the host every sim step.** `sim/sensors.py` calls it with
   `cpu().double().numpy()`, i.e. one device sync per step per batch. Correct, but it will
   cost real throughput at `num_envs = 2048`. Revisit before training: either compute
   lat/lon only on GPS epochs, or add a torch-side ENU→lat/lon in `common/frames.py` and
   keep the numpy one for the Pi.
2. **No sensor noise value is measured.** `pos_noise_m`, `vel_noise_mps`, `cog_noise_deg`,
   `latency_s`, `rate_hz`, `gyro_noise_dps`, `gyro_bias_dps`, `accel_noise_mps2`,
   `mag.noise_deg`, `mag.bias_deg`, `origin_lat/lon` are all placeholders. `SYSID.md` B9 /
   B10 are the procedures. `accel_noise_mps2` is parsed but unused — the 3-DOF planar sim
   has no accelerometer output.
3. **GPS COG is treated as north-referenced and CW**, and fed into heading only above
   `gps_heading_min_speed_mps`. INSPECTION H9 (`has_fix` can be false while RMC is valid)
   and H10 (first-fix sentinel `latitude == 0.0`) are properties of the Pi code, not of
   this model; the sim's `gps_valid` is a clean staleness flag, so the sim is *less*
   pessimistic than the vessel. Not fixable here.
4. **Heading convention (H1/H3) is unresolved.** The sim uses CONTRACT §1 (rad, 0 = north,
   CW) and the mag is treated as giving true heading. The real `155°` mount offset and
   `-1.5°` declination are unverified fudges; if the vessel's mag chain is mirrored, the
   sim's heading fusion is structurally right but sign-wrong.
5. **`wind.cd_area_m2`, `wind.max_speed_mps`, current speed/direction/drag and all wave
   amplitudes/frequencies are placeholders** (`SYSID.md` B11–B13). No disturbance level
   above 0 says anything about the real site.
6. Wave forces are applied as a body wrench of independent sinusoids with no coupling to
   the hull's motion or to the wave orbital velocity. Adequate for domain randomisation,
   not a seakeeping model.
