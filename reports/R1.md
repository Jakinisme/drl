## 1. New API (CONTRACT §4.1 / §4.4 names and order unchanged; only kwargs added)

### `sim/dynamics.py`

```python
Dynamics.set_params(env_ids,
                    mass_scale=None, inertia_scale=None, drag_scale=None,
                    quad_drag_scale=None) -> None      # quad_drag_scale is new
```

- Every `*_scale` accepts a **scalar**, a 0-d tensor, or a **`[k]` tensor/array** with one
  value per selected env (`k = len(env_ids)`, or `num_envs` when `env_ids is None`).
- `None` = that quantity stays nominal (i.e. `set_params(idx)` is equivalent to
  `reset(idx)` for mass/drag).
- Semantics kept from the old scalar version: `mass_scale` multiplies surge/sway inertia
  **and** their linear drag; `drag_scale` multiplies linear **and** quadratic drag of all
  three axes; `inertia_scale` multiplies yaw inertia only. `quad_drag_scale` (new) is an
  extra factor on the quadratic drag only, so linear/quadratic can be decorrelated.
- Wrong-length tensor raises `ValueError` instead of silently broadcasting.
- Internals: `M_env` / `D_lin_env` / `D_quad_env` were already `[N, 3]` and already used
  per env by `derivative()`/`step()`, so **no physics code changed** — only the writer.
  A randomised reset now really gives different `M`, `D_lin`, `D_quad` per row.

### `sim/sensors.py`

```python
SensorModel.set_noise(env_ids=None,
                      pos_noise_m=None, vel_noise_mps=None, cog_noise_deg=None,
                      gyro_noise_dps=None, gyro_bias_dps=None,
                      mag_noise_deg=None, mag_bias_deg=None,
                      gps_latency_s=None) -> None
```

- Same scalar / `[k]` broadcasting and `None` = "leave unchanged" rule; raises
  `ValueError` on a wrong-length tensor.
- Stored as per-env `[N]` tensors `pos_sigma_env`, `vel_sigma_env`, `cog_sigma_env`,
  `gyro_sigma_env`, `mag_sigma_env`, `gyro_bias_max_env`, `mag_bias_max_env`,
  `latency_env`; used inside `step()` / `reset()`.
- `gyro_bias_dps` / `mag_bias_deg` are the ± uniform **bound** and are drawn in
  `reset()`: they apply to the **next** reset of those envs. The sigmas and the GPS
  latency apply from the next `step()`.
- The pre-existing float attributes (`gps_pos_sigma`, `gps_latency`, `mag_bias_max`, ...)
  are **kept as the nominal yaml values** so `envs/asv_env.py:180-184`
  (`float(getattr(sen, key))`) keeps working unchanged.
- `self.gps_latency = <x>` assignments still work but are now **nominal only** — they no
  longer change behaviour. Any caller that set that attribute must switch to `set_noise`.

## 2. Per-env GPS latency — implementation choice

A single global queue length cannot serve per-env delays, so:

- one history ring `_buf: [N, L+1, 2]` where **col 0 = newest** true position, col `j` =
  position `j` steps ago; `L = max_i round(latency_i / dt)` over the batch (min 1 step,
  capped at 1024 steps = 20.5 s at dt 0.02 — `ponytail:` raise the cap if a latency above
  that is ever wanted, the gather is unaffected);
- per-env delay index `lag_i = round(latency_i/dt).clamp(1, 1024)`; the fix reads
  `buf[i, lag_i]` with one `torch.gather`, i.e. **no per-env Python loop**;
- the ring is rebuilt only when `L` changes, and `reset()` zeroes it exactly as before.

Identical-to-old behaviour with a uniform latency: the old code read `buf[:, -1]` of a
`lag+1` window, which is the same element as `buf[:, lag]` of a `L+1` window (`L >= lag`)
after the same roll; the `min 1 step` floor (`max(1, ...)`) is preserved, so
`latency_s = 0` still means one step of delay, as before. Verified bit-for-bit by
`test_randomisation_is_bit_identical_to_pre_change_snapshot`.
Cost: `N·(L+1)·2·4 B` — 2048 envs at 0.3 s max latency = ~0.5 MB.

## 5. Assumptions / TODOs

- Latency is quantised to whole sim steps (`round(latency/dt)`, floor 1 step), unchanged
  from before; `latency_s = 0` is therefore 0.02 s of delay, not zero.
- Per-env **GPS/IMU/mag rates** are *not* randomised (only noise, bias bound, latency);
  `rate_hz` stays a scalar per source. `ponytail:` add `rate_hz` to `set_noise` if rate
  randomisation is wanted — it needs per-env periods in `epoch()`.
- `reset()` still zeroes the delay ring, so after a reset an env with latency `> 0` reports
  position 0 for `lag` steps (pre-existing behaviour, preserved for bit-identity).
- `accel_noise_mps2` still has no consumer (no accelerometer in the 3-DOF output).
- Simulator numbers only; nothing here claims sim-to-real validity.
