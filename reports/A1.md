## Model as implemented

Thrusters, per motor `i` in firmware order NW, NE, SW, SE:

```
cmd_eff = cmd * [1, sway_sign, yaw_sign]
m_i     = motor_sign[i] * flip_i * (MIX[i] . cmd_eff)      flip_i = -1 if motor_invert[i]
m_i     = 0 if |m_i| <= deadband (0.03)                    then clamp(-1, 1)
m_i    += (target - m_i) * dt / lag_tau                    first-order lag, per env
F_i     = m_i >= 0 ? m_i * max_fwd * scale_fwd[i] : m_i * max_rev * scale_rev[i]
tau     = [ sum F_i*dir_i , sum (p_i x F_i*dir_i)_z ]
```

`mix_matrix` and `motor_invert` are read verbatim from the yaml and cross-checked against
`firmware-esp/src/header/config.h` by `test_mix_matrix_matches_firmware` when that file is
present. Nothing in the code "corrects" the firmware.

Dynamics:

```
M_eff * nu_dot = tau - D_lin*nu - D_quad*|nu|*nu - C(nu)*nu
x_dot   = u*sin(psi) + v*cos(psi)      (east)
y_dot   = u*cos(psi) - v*sin(psi)      (north)
psi_dot = r,  wrapped to [-pi, pi)
```

`M_eff` is diagonal (no off-diagonal added-mass coupling); linear drag is treated
implicitly in `step()`, so free decay stays monotone for any `dt`. `set_params` /
`reset` give the per-env mass, inertia and drag randomisation that CONTRACT §3.4 requires.

## Changes made this session

1. **`configs/vehicle.yaml:thrust_dir` was geometrically inconsistent with `mix_matrix`.**
   The sway row is `+1` on NW,SE and `-1` on NE,SW. The old directions gave NW and SW the
   same `y` sign, so a pure sway command summed to **exactly zero** sway force — a sim that
   cannot move sideways. Fixed by pairing NW with SE and NE with SW (`SE` flipped to
   `[0.707, -0.707]`), one value changed. The `TODO SYSID — INSPECTION H6` marker is kept
   on all four rows; this is a self-consistency fix, not a measurement.
2. **New test `test_pure_sway_produces_sway_force`** asserts the pairing, unit-length
   directions, and a nonzero sway force for a pure sway command with default signs.
3. Test-side indices: the NE motor (index 1) is flipped by `motor_invert`, so assertions
   that need positive motor values use indices `[0, 2, 3]` and NE is expected negative.
   Already the case in `test_ne_motor_is_inverted_by_firmware` and
   `test_deadband_is_esp32_level_per_motor`; both pass unchanged.

## OPEN ISSUES

1. **Does `MOTOR_INVERT[NE]` already compensate NE's physical spin, so the sim
   double-counts?** `config.h:100-105` inverts NE after mixing, and the sim applies the
   same flag. If the physical motor is mounted with reversed rotation such that the
   "inversion" is what makes it push the same way as the others, the sim is correct. If the
   inversion exists to cancel a reversed prop, the sim applies it twice and NE's force
   direction is wrong in every axis. **Not changed here.** Needs the bench check in
   `SYSID.md` B8: pure surge command on a thrust stand, measure NE's force direction. A
   wrong answer mirrors one corner of the vehicle silently.
2. **Pure sway produces large surge coupling.** `mix @ [0,1,0] = [+1,-1,-1,+1]`, and
   `MOTOR_INVERT[NE]` turns the NE term positive, so the firmware pattern is three motors
   forward and one reverse. With fwd/rev asymmetry that yields surge ≈ 15 N against sway
   ≈ 7 N for a full sway command. This is what the firmware matrix describes, not a bug in
   the model, but it means sway control will always fight surge. The test asserts the
   intended axis is nonzero and records the coupling; it does not assert dominance.
3. **H6 unresolved.** Which hull direction `+sway` and `+yaw` physically produce is still
   unknown (INSPECTION H6). `signs.sway_sign` / `signs.yaw_sign` default to `1.0` and are
   bench-only; `SYSID.md` B7 is the procedure.
4. **Every physical constant is a placeholder**: `mass_kg`, `inertia_izz_kgm2`,
   `added_mass.*`, `drag_linear.*`, `drag_quadratic.*`, `positions_m`, `thrust_dir`,
   `max_thrust_fwd_n`, `max_thrust_rev_n`, `lag_tau_s`, all `signs.*`. No experiment has
   been run. No sim result in this report may be applied to the real vessel.
5. Diagonal `M_eff` ignores off-diagonal added-mass coupling (marked with a `ponytail:`
   comment). Interface does not change when SYSID provides a full 3x3.
