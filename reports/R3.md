## 1. New `SensorModel.reset` API

```python
SensorModel.reset(env_ids=None, pos=None, heading=None) -> None
```

- `pos`: true ENU position [m], shape `[2]` or `[k, 2]` (`k = len(env_ids)`);
  `heading`: true yaw in **radians** (`state[:, 2]` convention), scalar or `[k]`.
  A wrong length raises `ValueError` (same style as `set_noise` / `_scales`).
- With `pos`: `pos_hat`, `gps_enu` and **every** delay slot of that env's GPS ring are
  set to `pos`; with `heading`: `heading` (rad) = `_wrap180(rad2deg(psi))`. `sog`, `cog`,
  `u`, `v`, `pos_init`, `mag_init` keep the old reset values, so the first real fix still
  snaps (`pos_init=False`) and the first mag sample still snaps the heading — the seeds are
  a prior, never a substitute for a measurement.
- `pos=None, heading=None` is **bit-identical** to the old zero-start reset; verified by
  `test_randomization.py::test_no_randomisation_is_bit_identical_to_pre_change_snapshot`
  (unchanged, still green).
- Consequence: the first `lag` fixes of every episode now report the spawn pose, so the
  estimator no longer starts at ENU (0, 0). Measured on 64 envs, one episode reset:

| | est→truth error at reset (max / mean) | after 5 policy steps (max) |
|---|---|---|
| pre-R3 (origin start) | **38.12 m / 21.77 m** | 10.81 m |
| R3 (pose-seeded) | **1.53 m / 0.52 m** | 0.77 m |

  0.52 m mean is the GPS position noise (`pos_noise_m = 0.4`) — the phantom error is gone.
  Same on CUDA (1.21 m / 0.48 m), so the seeding path is device-agnostic.

## 2. GPS ring allocated once

- `SensorModel.__init__(..., max_latency_s=None)`: `self.max_latency` = the largest delay
  any draw can produce. `None` -> nominal `gps.latency_s`.
- The ring is allocated on the **first `step()`** (which is where `dt` first exists):
  `cap = clamp(round(max(max_latency, max(latency_env)) / dt), 1, 1024)` steps,
  `self._buf` shape `[N, cap+1, 2]`. After that `cap` is frozen; `step()` only rolls.
- Per-env delay: `lag_i = round(latency_env/dt).clamp(1, cap)`, read with the **same single
  `torch.gather`** as before. Latency above `max_latency` is clamped to the ring instead of
  silently reallocating it (see §7).
- `reset()` writes only `self._buf[idx]`, so a partial reset cannot touch another env's
  history and cannot change the shape. The env passes
  `max_latency_s = sensors.yaml gps.latency_s + env.yaml sensor_latency_s = 0.2 + 0.1`,
  i.e. `cap = 15` steps (0.3 s) at `dt = 0.02`, `[N, 16, 2]` = **256 KB at 2048 envs**
  (was 0.5 MB at the old 1024-step cap only in theory; in practice the old ring was
  batch-max sized and got rebuilt).
- Regression guard: `tests/test_sensors.py::test_partial_reset_with_larger_latency_keeps_other_envs_gps_history`
  — env 0's ring rows are `torch.equal` before/after a reset of env 1 with a 20-step
  latency, shape unchanged, env 0 keeps its own 1-step lag, env 1 reports its seeded spawn.

## 3. Bias: one source, no number changed

- **Kept: `configs/sensors.yaml:mag.bias_deg = 5.0`**, consumed by `SensorModel.mag_bias_max`
  -> `mag_bias_max_env` -> the per-episode uniform draw in `reset()`. That is the value the
  sensor model actually uses, so it is the one that stays.
- **Dropped: `configs/env.yaml:sensor_bias_deg`** — `envs/asv_env.py` no longer reads it at
  all (no `self.r_bias_deg`, gone from the `randomize` gate too). The env now draws
  `mag_bias_deg = _mag_bias0 * (1 + U(-1,1)*r_noise)` with
  `_mag_bias0 = float(sensors.mag_bias_max)`; that is the same formula R2 used, only the
  centre moved from the env.yaml copy to the sensors.yaml original. Both were 5.0, so
  **no numeric value changed** on the shipped configs, and `sensor_noise` (not the bias
  key) now drives the ±spread, as it already did.
- `configs/env.yaml` is **not** edited (not mine): its `sensor_bias_deg: 5.0` line is now a
  dead key and should be deleted or re-commented by the config owner.
- Guarded by `test_env_randomization.py` (ZERO_KEYS no longer lists `sensor_bias_deg`)
  and by the source scan that no nominal sensor attribute is written from the env.

## 4. `set_params`: mass and drag decoupled (R2 §2 table obsolete)

`sim/dynamics.py::set_params` no longer multiplies `D_lin`/`D_quad` of x,y by
`mass_scale` — one deleted line. With `ms = mass_scale`, `ins = inertia_scale`,
`ds = drag_scale`, `qs = quad_drag_scale` (`None` = 1):

| tensor | x (surge) | y (sway) | n (yaw) |
|---|---|---|---|
| `M_env` | `M·ms` | `M·ms` | `M·ins` |
| `D_lin_env` | `DL·ds` | `DL·ds` | `DL·ds` |
| `D_quad_env` | `DQ·ds·qs` | `DQ·ds·qs` | `DQ·ds·qs` |

Nominal placeholder vehicle (`M = 15, 20, 1.8`, `D_lin = 6, 18, 1.5`, `D_quad = 4, 12, 0.8`)
with `ms = 1.3, ins = 0.8, ds = 1.2` (measured on the tensors):

| | x | y | n |
|---|---|---|---|
| `M_env` | 19.5 | 26.0 | 1.44 |
| `D_lin_env` | **7.20** (R2: 9.36) | **21.60** (R2: 28.08) | 1.80 |
| `D_quad_env` | **4.80** (R2: 6.24) | **14.40** (R2: 18.72) | 0.96 |

Semantic change to record: the surge/sway drag factor is `ds ∈ [0.70, 1.30]` again, i.e.
exactly `configs/env.yaml:drag`, instead of R2's `ms·ds ∈ [0.49, 1.69]`. R2 §2's table and
its "heavier hull is also a draggier one" note are **wrong from now on**; the `drag` range
in `env.yaml` now means what it says again.

Tests touched for this: `tests/test_randomization.py::test_dynamics_per_env_mass_and_drag_change_step_response`
(closed form now `dl = dl0·ds`, `dq = dq0·ds`) and
`tests/test_env_randomization.py::test_effective_factors_on_mass_and_drag_are_the_documented_ones`
(the table above; env path asserts the drag factor equals `drag_scale` on all three axes and
stays inside `r_drag`). `tests/test_env.py::test_domain_randomization_ranges` still passes
untouched — its drag bound was the wider `r_mass+r_drag+r_mass·r_drag`, which merely becomes
loose; tightening it belongs to the env owner.

## 7. Assumptions / open items

- Latency is still quantised to whole steps with a 1-step floor (`latency_s = 0` = 0.02 s of
  delay), unchanged from R1/R2.
- `max_latency_s` is the contract: a caller that raises `latency_env` above it gets the delay
  clamped to the ring length (no reallocation, no error). The env passes the true yaml
  maximum, so this only bites direct `SensorModel` users.
- The ring is sized for the batch and never shrinks; cost is `N·(cap+1)·2·4 B`
  (`256 KB` at 2048 envs, `cap = 15`). A much wider `sensor_latency_s` range in env.yaml
  grows memory linearly — `ponytail:` lower the cap only if a latency range > 20 s is ever
  needed.
- `configs/env.yaml:sensor_bias_deg` is a dead key now (owner: config/env agent).
- `tests/test_env.py::test_domain_randomization_ranges`'s drag bound is now loose; not
  tightened here (file not in this unit's ownership).
- Simulation only. None of these numbers says anything about the real vessel; every
  physical/noise constant is still `TODO SYSID`.
