## How the port works

```
est  [B,6] = (x_e, y_n, psi_rad, u, v, r)            CONTRACT §2 layout, radians
goal [B,4] = (x_goal_e, y_goal_n, psi_goal_rad, mode)  mode 0 waypoint, 1 station keeping
act() -> action [B,3] = (surge, sway, yaw) in [-1,1]   same numbers the ESP32 gets
```

Per env, three PID recurrences (north, east, heading) hold integrator, previous error
and filtered derivative as `[B]`/`[B,2]` tensors, so one `act()` call is the whole
batch. The recurrence is `pid.py:89-113` verbatim: clamp integral, filtered derivative
with coeff `0.1`, `p + i + d`, clamp output. `dt` is clamped to `[0.001, 0.5]` like
`pid.py:80-81`.

Mode handling matches `ThrustComputer.compute()`: waypoint mode steps the heading PID
only; station keeping steps all three. One heading PID instance serves both modes, as
in the original. `reset()` zeroes everything.

Waypoint mode (`navigation.py:163-204` + `thrust.py:128-149`): bearing to the goal is
recomputed as `atan2(dx_e, dy_n)` in compass degrees (that is what the navigator passes
to the PID, and CONTRACT §5 says `goal[2]` holds exactly that, so `goal[2]` is unused
here); speed = 0.55 m/s tapered by `max(0.2, dist/5)` inside 5 m; surge =
`speed*heading_factor/0.55` with `heading_factor = max(0.25, 1-|err_deg|/150)`; surge
forced to 0 and only yaw kept beyond 100°.

Station keeping (`navigation.py:206-225` + `thrust.py:151-172`): measurement =
`actual - hold` per axis with the 0.5 m DP deadband, PID setpoint 0 (so the error is
`hold - actual`), then NED→body with the compass-heading rotation. Confirmed equal to
`common.frames.enu_to_body(east_cmd, north_cmd, psi)`.

Output stage is `thrust.py:112-124`: per-axis deadband 0.05, then clamp to ±1.

## Differences from the Pi code (all deliberate)

1. **`u, v` are ignored.** `thrust.py` has no velocity term at all (INSPECTION H7);
   adding damping would be a new controller, not a port. The `est` columns 3-4 are
   accepted and unused.
2. **`dt` is an argument** (default 0.1 s = policy rate). The Pi version derives `dt`
   from the wall clock inside `PIDController.compute()`, defaulting to 0.05 on the first
   call. Consequence: a multi-step comparison needs a frozen clock, and the first
   reference step uses 0.05 (see the parity test).
3. **No navigator state machine.** `mode` and the goal arrive per env from the env /
   `evaluate.py` (CONTRACT §4.6), so waypoint lists and the arrival advance live
   outside; nothing advances the goal here.
4. **No action-rate limit and no `prev_action` use.** CONTRACT §4.6 gives that to the env.
5. **Radians instead of degrees at the interface** (CONTRACT §1). Degrees reappear only
   inside, to feed the PID terms copied from `pid.py`/`config.py`.
6. **`output_deadband` is a constructor argument, default 0.05** so the port stays
   bit-faithful. TODO(H4): 0.05 is a Pi-side convenience, **not** the actuator deadband —
   the hardware deadband is 0.03 per mixed motor (`config.h:110`, CONTRACT §4.2, owned by
   `sim/thrusters.py`). `PIDBaseline(output_deadband=0.0)` removes the chop, and any
   PID-vs-PPO comparison should report which of the two it used.
7. **Gains and shaping constants are module-level mirrors** of `config.py`, not a config
   file: they are measured facts of the existing boat and A3 owns no YAML.

## Parity testing

`tests/test_pid_parity.py` imports the real `pi-control/src/control/thrust.py`
read-only. That import fails on Windows as-is: `thrust.py` pulls
`src.sensors.fusion`, which needs pyserial/smbus/pigpio (INSPECTION H12). Three
hardware-only modules are stubbed in `sys.modules` before the import — `src.sensors`
(package shell), `src.sensors.fusion` (`FusedState` dataclass) and `src.utils.logger`
(`setup_logger` without the rotating file handler). Everything that *computes* —
`src.config`, `src.utils.geo`, `src.control.pid`, `src.control.navigation`,
`src.control.thrust` — is the unmodified file, so this is code-vs-code.

What is compared, tolerance `atol = 1e-4` on the normalised command (`rtol = 0`,
float32 port vs float64 reference plus a rad→deg round trip on the heading):

* **station keeping, single step**, 5 fixed cases in one batched call vs 5 fresh
  navigator+thrust cycles: heading error across the 0/360 seam, an axis inside the
  0.5 m DP deadband, a 180° heading error, everything inside a deadband, a small
  near-north error.
* **waypoint, single step**, 5 fixed cases: far dead ahead (surge 1.0), 69° off-bow
  (taper), inside the slowdown radius, goal behind (turn in place, surge 0), short hop.
* **station keeping, 8 steps at dt = 0.1**, wall clock frozen (`pid.py`'s `time`
  reference replaced) and `_last_time` primed per PID so `dt` is exact: exercises
  integrator growth, integral clamping, the filtered derivative and the 0.05 output
  deadband crossing (step 6 lands at 0.036 and both implementations zero it).
* **waypoint, 8 steps at dt = 0.1**: the real navigator drives speed and heading each
  cycle, so haversine distance vs `hypot` and spherical bearing vs `atan2` are inside
  the comparison (agreement ~1e-9 over these distances).
* **interface contract**: output shape/dtype/range, deadband zeroing, sway = 0 in
  waypoint mode, and `reset()` reproducibility.

All 4 parity tests pass at `atol = 1e-4`; measured max deviation over the two
single-step batches is **3.0e-7** (float32 epsilon), and the 8-step traces agree to the
same order, so the tolerance has four orders of margin.

## Closed-loop stability (toy plant, not the sim)

First-order body-velocity plant (τ = 0.4 s, u_max 0.7 m/s, r_max 0.6 rad/s) integrated
at 0.02 s with the controller at 10 Hz. Measured:

```
station keeping, hold (5,3), 60 s : radial error 0.688 m, stable over the next 10 s,
                                    hull heading 0.000° (no disturbance in the plant)
station keeping, deadband off    : 0.700 m   -> the offset is the DP deadband, not tuning
waypoint 23.6 m away             : inside 2 m at t = 33.3 s, final distance 0.094 m
```

This is a toy plant. It says the ported controller still closes the loop; it says
nothing about the vessel.

## Bugs and oddities found (reported, not fixed)

1. **H4 confirmed empirically.** The 0.05 output deadband does real work: in the
   multi-step parity trace a correctly computed surge of 0.036 is thrown away by the Pi
   before the ESP32 sees it (that step only matches because the port keeps the same
   deadband). This is the "small station-keeping command silently becomes zero" case.
2. **The 0.5 m DP deadband is per axis, so the radial offset can be 0.707 m.** The
   0.688 m steady-state error above is `0.5·√2`, i.e. the controller parks on the
   deadband corner. Not a code bug, but it means the PID baseline cannot hold better
   than ~0.7 m in still water by construction, whatever the gains are.
3. **Derivative kick on every reset / mode switch (H11 second half).** `pid.py:58-63`
   zeroes `_prev_error` and `_prev_derivative` but not the scale of the first error, so
   the first D term after a reset is `kd·err/dt` — with `dt = 0.05` and `kd = 0.3` that
   is `6·err`, six times the proportional term. `thrust.py` never calls `reset()` on a
   normal mode change, so it mostly hits IDLE→active transitions. Kept as-is for
   parity; a real fix belongs in `pid.py`, which is read-only here.
4. **`set_heading_mode()` does not reset `_prev_error`** (H11): switching mode leaves a
   stale error of the wrong units (degrees of a wrapped error vs degrees of an
   unwrapped one). Only reachable through `ThrustComputer.__init__`, so no effect today.
5. **Waypoint mode has no integral on position and no cross-track term.** It is
   open-loop in surge (speed command, not speed control): against current it will hold a
   steady cross-track offset and never correct it, because the only feedback is the
   bearing, which points at the waypoint from wherever the boat happens to be. This is
   the main structural difference from the RL policy's observation/reward, and the
   reason to expect a large PID-vs-PPO gap in the wave/current scenarios of wave 4.
6. **`speed_norm` is `WAYPOINT_MAX_SPEED` itself** (`thrust.py:146-147`), so `surge` is
   `heading_factor · speed_ratio` and the 0.55 cancels. Harmless, but it means the
   "normalise by hull speed" comment is a no-op and changing `WAYPOINT_MAX_SPEED` does
   not rescale the command.
7. **`compute()` applies the deadband and clamp to `MANUAL` too**, so a joystick command
   below 0.05 is silently zeroed — same H4 family, out of scope here.
8. **H1 (heading rotation sense) is inherited, not introduced.** The port uses
   CONTRACT §1 (`psi` rad, 0 = north, CW) and the same compass rotation as
   `thrust.py:164-167`. If the vessel's fused heading is really CCW (INSPECTION H1),
   both the PID and the sim are wrong together, and this parity test cannot see it.
