## 2. Effective factors on M, D_lin, D_quad — and where they differ from the old writer

Given `mass_scale = ms`, `inertia_scale = ins`, `drag_scale = ds`
(`quad_drag_scale` left `None`), per axis `(x, y, n)`:

| quantity | x | y | n |
|---|---|---|---|
| `M_env` (new = `set_params`) | `M·ms` | `M·ms` | `M·ins` |
| `D_lin_env` (new) | `DL·ms·ds` | `DL·ms·ds` | `DL·ds` |
| `D_quad_env` (new) | `DQ·ms·ds` | `DQ·ms·ds` | `DQ·ds` |
| `M_env` (old writer) | `M·ms` | `M·ms` | `M·ins` |
| `D_lin_env` (old writer) | `DL·ds` | `DL·ds` | `DL·ds` |
| `D_quad_env` (old writer) | `DQ·ds` | `DQ·ds` | `DQ·ds` |

So: **mass and inertia match exactly; surge/sway drag does not.** The old env writer
multiplied all three drag axes by `drag_scale` only, i.e. mass and drag were independent.
`Dynamics.set_params` couples them — `D_lin[:, :2] = M[:, :2]·ms·ds` and
`D_quad[:, :2] = DQ·ms·ds` — so a heavy hull is also a draggy one. This also contradicts
R1 §3 row 3's parenthetical "identical maths … as the old writer did": the *old* writer
never scaled drag by `mass_scale`, so the drag of x/y in the old code was off by exactly
a factor `ms` (in 0.70…1.30 with the yaml range).

Numeric example on the placeholder vehicle (`M = 15, 20, 1.8`, `D_lin = 6, 18, 1.5`,
`D_quad = 4, 12, 0.8`) with `ms = 1.3, ins = 0.8, ds = 1.2`:

| | new `M` | old `M` | new `D_lin` | old `D_lin` | new `D_quad` | old `D_quad` |
|---|---|---|---|---|---|---|
| x | 19.5 | 19.5 | **9.36** | 7.20 | **6.24** | 4.80 |
| y | 26.0 | 26.0 | **28.08** | 21.60 | **18.72** | 14.40 |
| n | 1.44 | 1.44 | 1.80 | 1.80 | 0.96 | 0.96 |

Range of the surge/sway drag factor: old `ds ∈ [0.70, 1.30]`, new `ms·ds ∈ [0.49, 1.69]`
(`r_mass = r_drag = 0.30`). If the contract ever wants the old decoupling back, pass
`drag_scale = ds / ms` from the env or use `quad_drag_scale` for the quadratic part —
neither is done here, R2 applies R1's call site as written.

Asserted directly on the tensors by
`tests/test_env_randomization.py::test_effective_factors_on_mass_and_drag_are_the_documented_ones`
(`M_env/M`, `D_lin_env/D_lin`, `D_quad_env/D_quad` vs the table above, 1e-6) and by the
env reset path (`ratio_L[:, :2] == ratio_M[:, :2] · ratio_L[:, 2]`, 1e-5).

## 3. "Randomisation off" = nominal, no draws

A `randomization:` block of all zeros sets `env.randomize = False`, and `reset()` then
skips `_randomize` / `_sensor_randomization` entirely: params stay nominal yaml values
(`dynamics.reset` / `thrusters.reset` already do that; sensor nominal comes from
`SensorModel.__init__`). This is what makes the bit-identity test possible at all — the
old batch-wide writer forced `mag_bias_max = sensor_bias_deg` even when every range was
0, and `set_noise(mag_bias_deg=0)` would zero the magnetometer bias, both deviations
from nominal.

Side effect to know about: with randomisation on, a reset now consumes `3k` (mass/inertia/
drag) `+ 2k·4` (thruster) `+ 3k` (weak/lag/deadband) `+ 4k` (sensor) draws from `env._gen`
where the old code consumed `3k + 2k·4 + 3k + 2` scalars. Same seed therefore gives a
*different* second-reset spawn than the pre-change env. The identity test uses the
construction reset (the one place both versions draw the same sequence) and does not
re-reset — see the test for the exact procedure.

## 4. Sensor side, per env

| `sensors.set_noise` kwarg | source | applied |
|---|---|---|
| `pos_noise_m`, `vel_noise_mps`, `cog_noise_deg`, `gyro_noise_dps`, `mag_noise_deg` | yaml nominal `× (1 + U(-r_noise, r_noise))`, one factor per env | next `step()` |
| `gyro_bias_dps` | `gyro_bias_dps` (yaml) `× (1 + U·r_noise)` as the ± bound | next `reset()` (before it, §1 row 1) |
| `mag_bias_deg` | `sensor_bias_deg` (env.yaml = 5.0) `× (1 + U·r_noise)` as the ± bound | next `reset()` |
| `gps_latency_s` | `latency_s + U(-r_latency, r_latency)`, clamped ≥ 0 | next `step()` |

`mag_bias_deg` keeps R1 §3 row 4's formula (`r_bias_deg·(1+U·r_noise)`), not a value
centred on `sensors.yaml:mag.bias_deg`. At the shipped configs both are 5.0, so nothing
moves today, but the two numbers are independent sources of truth for the same physical
quantity (see §6).

## 5. Findings — reported, not fixed

1. **`SensorModel.reset` takes no initial position.** Signature is `reset(env_ids=None)`
   only; it zeroes `gps_enu`, `pos_hat`, `u`, `v`, `heading`, ages and the delay ring.
   The env calls `self.sensors.reset(idx)` and has no way to seed it with the spawn
   `(x, y, psi)`, so the estimator restarts at the ENU origin.
2. **GPS ring after reset.** `reset()` zeroes `_buf`, and `lag_i = round(latency/dt)`
   is clamped to ≥ 1 step, so for the first `lag` sim steps after a reset the fix is the
   zeroed column, i.e. **ENU (0, 0)** (→ `gps_lat/lon` at the model origin), not the
   spawn. Measured with the shipped `latency_s = 0.2`, `dt = 0.02` (`lag = 10`): right
   after `reset()` the env's primed sample gives `est xy ≈ (0.18, 0.07)` while the true
   state is `(1.15, 18.61)`; `pos_hat` snaps to that first fix (`gps_alpha` snap), so
   the first policy step sees a position error of the spawn distance and it decays over
   ~10 sim steps (2 policy steps). At step 9–10 `est` rejoins the truth. Pre-existing
   in R1 (kept for bit-identity) but it is a real episode-start artefact.
   Nuance: on the very first `step()` after construction `_buf` is rebuilt from the
   current position, so the first episode of a fresh env reports the true position
   immediately and later episodes do not — inconsistent between first and subsequent
   episodes.
3. **Per-env latency can reallocate the ring.** `step()` rebuilds `_buf` whenever the
   batch-max lag changes; a partial reset that raises `latency_env` for one env wipes
   the GPS history of the whole batch (their fixes jump to the current position).
   R1's mechanic, not exercised by the current tests.
4. `gps_latency_s = 0` still means one step (0.02 s) of delay — R1 §5, unchanged.

## 6. Assumptions / TODOs

- `sensor_bias_deg` (env.yaml) and `sensors.yaml:mag.bias_deg` both claim to be the
  magnetometer bias magnitude; only the env.yaml one is used when randomisation is on,
  only the sensors.yaml one when it is off. Owner of the configs should collapse them.
- Every randomised range is still a TODO SYSID placeholder; nothing here is validated
  against the vessel.
- Derived from §2: the mass/drag coupling makes the surge/sway drag prior `±30 %` wider
  than `configs/env.yaml:drag` alone suggests. Whoever tunes `drag` for sim-to-real
  should know this.
- Simulation only; no claim that these distributions transfer to the real ASV.
