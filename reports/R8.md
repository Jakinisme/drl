## 0. TL;DR

- The reward is redesigned: speed-gated arrival, dense hold bonus, saturation penalty, three
  weights retuned. Physics, observation, action space and network are untouched.
- The **control arm reproduces the pre-R8 reward bit for bit**: max |diff| = `0.000e+00` over
  400 steps × 16 envs driven by the R7 policy. Verified twice, before and after the final
  floor fix.
- A sixth bug was found and fixed **before** R8 built on it: `station_keeping_fraction` was
  drawn from `U(-1,1)`, so `0.3` realised `0.65`. Committed separately (`92b529d`).
- No training was launched. Nothing was committed except that one bug fix.

## 1. Prerequisite findings (V1)

1. **Arrival bonus is a pure constant.** `envs/asv_env.py:458-459` pays
   `w_arrival * arrive_evt`, `w_arrival = 10.0`, with no speed, distance or heading
   dependence. The latch is `enter = final & (d < 2.0) & ~final_latch`, cleared per reset.
   Flying through at speed pays exactly what stopping pays.
2. **Measured speed at arrival** (R7 `ckpt_last`, CPU, 8 envs): at the final goal first
   entry, n=38, mean **1.002**, p50 0.999, p95 **1.335**, max **1.468** m/s — all above the
   reward's own `max_surge_mps = 1.0` scale. Intermediate arrivals are rare in the harness
   (see §2), so that distribution is not meaningful.
3. **`settled_pct` is binary per episode** (100/0), then averaged; `settling_time_s` needs a
   ≥5 s in-band tail (`hold_s`), `tol` defaults to 1.0 m. A pass-through that ends the trace
   mid-leg always reads `inf`. Entry speed is invisible to both.
4. **Disturbance seeding was constant** with respect to `--seed`: `--seed 0` vs `--seed 1234`
   gave a wind/wave max abs diff of exactly **0.0** while spawn moved 45.15 m. Cross-seed
   comparisons of disturbance-bound scenarios meant nothing before this.

## 2. The bug that had to come first (not in the brief)

`envs/asv_env.py:276` drew the episode mode with `self._unif(k) < self.sk_frac`, but `_unif`
returns `U(-1,1)`, not `U(0,1)`. The realised station-keeping fraction was therefore
`(sk_frac + 1) / 2`:

| requested | realised (20 000 envs, seed 0) | after fix |
|---|---|---|
| 0.00 | 0.5014 | 0.0000 |
| 0.30 | 0.6520 | 0.2997 |
| 0.90 | 0.9520 | 0.9021 |
| 1.00 | 1.0000 | 1.0000 |

So every R4–R7 training run saw roughly **twice** the station keeping its config asked for.
`evaluate.py` was unaffected because it overwrites `env.mode` from the scenario — which is
exactly why the eval numbers looked sane and only the training mix was wrong.

The same file already handled this correctly for the weak-thruster draw
(`2 * r_weak_prob - 1`, line 339), so it was an inconsistency, not a misunderstanding.

Fixed separately in commit `92b529d` with `tests/test_env_mode_fraction.py` (9 cases; 7 of
them fail when the old draw is restored). The RNG-sensitive golden snapshot
`tests/test_env_randomization.py::PRE_CHANGE_HASH` moved with it — expected, since the mode
draw consumes a different stream position; the snapshot's own property (randomisation off
gives nominal params and a reproducible rollout) is unchanged.

**Consequence:** R4–R7 checkpoints were trained on a different episode mix than their config
claims. Nothing before `92b529d` is like-for-like with anything after it.

## 3. Reward changes (A)

New keys under `reward:` in `configs/env.yaml`, each marked `# TODO T8 placeholder, untuned`:
`arrive_gate_floor 0.3`, `settle_speed_ref_mps 0.4`, `w_hold 0.5`, `hold_radius_m 1.5`,
`w_sat 0.1`. Retuned: `w_action_rate 0.05 → 0.15`, `w_energy 0.01 → 0.02`,
`w_near_goal_speed 0.1 → 0.3`.

```
gate(speed, ref) = exp(-(speed / ref)^2)

intermediate WP arrival : w_arrival * (arrive_gate_floor + (1 - arrive_gate_floor) * gate)
FINAL WP arrival        : w_arrival * gate                     (no floor)
hold bonus (final goal) : w_hold * [d < hold_radius_m] * gate(speed, settle_speed_ref_mps)
saturation penalty      : -w_sat * mean_axes( relu(|a| - 0.8) / 0.2 )^2
```

### 3.1 The final-waypoint floor — I overrode the sub-agent here

The brief specifies a floor for intermediate waypoints and *"gate only"* for the final one,
but both share a single `arrive_evt`, so the two clauses cannot both hold literally. The
sub-agent implemented the common formula, which applied the floor to **both** — the final
waypoint still paid 3.0 at 1.47 m/s.

That defeats the point of R8. Landing is the behaviour R7 never learned; a fast fly-through
must not still collect a third of the prize. I added `_arrival_is_final`, a per-env flag set
in `_arrive_evt`, so the floor applies to intermediate crossings only. Measured after:

| event | speed | pays | % of `w_arrival` |
|---|---|---|---|
| intermediate | 0.0 | 10.0000 | 100.00 |
| intermediate | 1.0 | 3.0135 | 30.14 |
| intermediate | 1.47 | 3.0000 | 30.00 |
| **final** | 0.0 | 10.0000 | 100.00 |
| **final** | 1.0 | 0.0193 | **0.19** |
| **final** | 1.47 | 0.0000 | **0.00** |
| control, any | any | 10.0000 | 100.00 |

Control still pays the full 10.0 at every speed, i.e. the pre-R8 behaviour survives.

### 3.2 Bit-compatibility

Verified independently, twice: `git show HEAD:envs/asv_env.py` and the working tree, both
driven by the R7 policy with actions held identical, comparing `_reward` output directly.

```
400 steps x 16 envs, R7 policy driving both:
  max |reward HEAD - reward control| = 0.000e+00
```

Note on how to *not* measure this: the first attempt instantiated both envs without resetting
the global torch RNG, so sensor randomisation drew different `gyro_bias`/`mag_bias` and the
observation stream diverged by 1.35. That was a harness artefact, not a reward difference.
Seeding `torch.manual_seed` before each construction gives bit-identical observations.

### 3.3 The `settle_speed_ref_mps` trap (two of them)

`1e6` does **not** give `gate == 1.0`. In float32, `exp(-(1000/1e6)^2) = 0.99999905`, not
1.0, so the control arm would silently stop matching the pre-R8 reward. `1e20` is exact for
every `|v| < 1e18` and is what both `configs/env.yaml` and the control variant now use.

Separately, **PyYAML parses `1e20` and `1.0e20` as strings**, not floats. `_gate` then saw a
`str` and returned 1.0 for every speed, making the gate inert while looking configured. The
value is now written as digits (`100000000000000000000`), `_gate` coerces its ref to a
tensor, and `tools/make_r8_variants.py` writes digits too. Verified: every key in all three
variants loads as `int`/`float`.

### 3.4 Can the new reward actually change behaviour?

The sub-agent's arithmetic: with γ=0.99, effective horizon ~100 steps, Σγᵗ over 1200 steps
= 100.0, so the dense hold bonus of 0.5/step is worth ~50 — it is not outgunned by the
one-shot arrival. At R7's measured arrival speeds, pass-through pays ~3.0 (now 0.0 after the
floor fix) against ~60 for settling: **~20× in favour of stopping**.

Stated risk, not resolved: the hold zone (1.5 m radius) is **0.19 % of the waypoint box**
(`waypoint_radius_m: 35.0`), and the smoke shows the `hold` component flat until t≈400. The
signal is sparse; whether 10M steps find it is an empirical question this task does not
answer.

## 4. Variants (B) — not trained

`tools/make_r8_variants.py` generates `configs/r8/env_{control,A,B}.yaml` and
`train_{control,A,B}.yaml` by line-level patching of the `reward:` block, so comments and key
order survive. Idempotent (byte-identical re-runs), refuses to overwrite files it did not
generate. `--verify` passes.

| variant | arrive_gate_floor | settle_speed_ref | w_hold | hold_radius | w_sat | w_action_rate | w_energy | w_near_goal_speed |
|---|---|---|---|---|---|---|---|---|
| control | 1.0 | 1e20 | 0 | — | 0 | 0.05 | 0.01 | 0.1 |
| A | 0.3 | 0.4 | 0.5 | 1.5 | 0.1 | 0.15 | 0.02 | 0.3 |
| B | 0.15 | 0.25 | 1.0 | 1.0 | 0.2 | 0.20 | 0.02 | 0.5 |

Launch (PowerShell, repo root) — only `--config`; every value lives in the yaml, and CLI flags
would override it:

```powershell
./.venv/Scripts/python.exe train.py --config configs/r8/train_control.yaml
./.venv/Scripts/python.exe train.py --config configs/r8/train_A.yaml
./.venv/Scripts/python.exe train.py --config configs/r8/train_B.yaml
```

Evaluate:

```powershell
./.venv/Scripts/python.exe evaluate.py --ckpt runs/r8_A/ckpt/ckpt_last.pt --scenarios sk_wind,wp_square --episode-s 300 --dwell-stay-factor 1.0 --seeds 4 --out results_r8_A
```

Flags confirmed against `evaluate.py` argparse. Caveat carried from V2: `evaluate.py` has no
env-config flag and hardcodes `configs/env.yaml`, so evaluation uses the R8 default reward
for all three arms — deliberate, it keeps the reference environment identical. It also means
the reward used at eval is not the reward each arm trained under.

### 4.1 Decision rule, fixed before any result exists

- **Primary:** `sk_wind` `settled_pct` (higher better) and `hold_rms_m` (lower better).
- **Secondary:** `wp_square` `waypoints_reached` and `lap_completed`.
- **Guards:** `sat_frac` and `reversal_rate` must drop vs control; `waypoints_reached` must
  not fall more than 15 % relative to control; no variant may have more geofence-dropped
  episodes than control.

A variant wins only if it beats control on the primary metric **and** passes every guard.

## 5. New eval metrics (C)

Appended at the end of `evalkit/metrics.py::summarize()` and of every output; no existing
column changed:

`sat_frac` (fraction of steps with max-axis |a| > 0.9), `reversal_rate` (surge sign changes
per minute with |a_surge| > 0.5 on both sides), `arrival_speed_mean_mps`, `hold_rms_m`,
`hold_p95_m` (radial error over the last 30 s of a final hold).

Two fixes on top of the sub-agent's work:

- **`arrival_speed_mean_mps` returned NaN whenever any single waypoint's entry speed was
  undefined** — one corner entered on the last sample poisoned the whole average, which is
  not what its own docstring promised ("per-waypoint nans dropped") and is why the column
  read `NOT AVAILABLE` on the R7 baseline gate run. Now individual undefined entries are
  dropped; NaN only when nothing usable remains.
- `evaluate.py`'s `plots()` did `int(nan)` for no-plan scenarios, crashing any run that
  reached plotting. Now `-1`.

## 7. Behaviour gate (E)

`tools/gate_policy.py --ckpt <path>` runs sk_wind and wp_square at the pinned strict settings
and prints PASS/FAIL against `configs/gates.yaml`; exit non-zero on any FAIL or NOT AVAILABLE.
It reads the new metrics defensively, so a missing column fails rather than silently passing.

Real R7 baseline, 4 seeds × 8 envs × 2 scenarios, 32 complete episodes each, exit 1:

```
sk_wind    settled_pct               min        0        FAIL
sk_wind    hold_rms_m                max        NOT AVAILABLE
sk_wind    sat_frac                  max        0.713    FAIL
sk_wind    reversal_rate             max        0        PASS
sk_wind    arrival_speed_mean_mps    max        NOT AVAILABLE
sk_wind    geofence_dropped_episodes max        0        PASS
wp_square  waypoints_reached         min        3.84     PASS
wp_square  lap_completed             min        0.906    PASS
wp_square  sat_frac                  max        0.755    FAIL
```

This is the gate working: R7 **passes** the waypoint rows (which is how it shipped as "R7
works") and **fails every settling row** at 71–76 % actuator saturation.

All nine thresholds are **guesses with no calibration data**. Critically, the `wp_square`
block passes for a policy that never settles, so a green `wp_square` is not evidence of a
usable controller; only `sk_wind.settled_pct` and the two `sat_frac` rows discriminate today.

## 8.1 NaN smoke (variant A, 20 iters x 256 envs x 64 steps)

All rewards finite. Per-component means are bounded and no term dominates by orders of
magnitude, which is what the smoke exists to show:

| component | range of per-iteration mean |
|---|---|
| position | +0.038 … +0.046 |
| fine | +0.0004 … +0.0009 |
| heading | +0.044 … +0.067 |
| cross-track | −0.012 … −0.215 |
| near-goal speed | ~−0.0002 |
| saturation | ~−0.0001 |
| total reward | −0.148 … +0.090 |

`arrive`, `hold`, `progress`, `action_rate`, `energy` read ~0 across the run because **random
actions never approach the goal** — this smoke cannot exercise those terms, and it is not
evidence that they are reachable. Their behaviour is instead pinned by the direct probes in
§3.1 (arrival pays 0.19 % / 0.00 % at speed; control pays 10.0 always) and by
`tests/test_reward.py`. Anyone reading this table should not conclude the hold term is inert.

## 9. Report-only items (not fixed here)

1. **Is sk_wind bounded by thrust?** Placeholder `9.8 N` vs unmeasured bollard pull
   (SYSID B7). Not estimated here — it needs the wind force arithmetic against
   `max_surge_mps` and the drag model, and any answer built on a placeholder thrust number

3. **History K = 10 (1 s)** against steady wind/current is short. GRU suggestion only.
4. **The Pi navigator goes IDLE after the last waypoint** while training expects a hold.
   Recommended Pi-side change; not made here.
5. **No behaviour gate existed before this task.** That is how a pass-through policy shipped
   as "R7 works". `tools/gate_policy.py` closes the gap; the thresholds still need calibrating
   against a policy that genuinely settles.
