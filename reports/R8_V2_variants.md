## Which keys each variant changes

Every other key of the `reward:` block is copied through unchanged from `configs/env.yaml`.
The two new weights `w_hold` and `w_sat` carry `# TODO T8 placeholder, untuned`; all other
values are untuned too — the tag marks the keys that did not exist before R8.

| key | env.yaml (pre-R8) | control | A | B |
|---|---|---|---|---|
| `w_hold` | absent → term off | **0** | **0.5** | **1.0** |
| `hold_radius_m` | absent | absent (no hold term) | **1.5** | **1.0** |
| `w_sat` | absent → term off | **0** | **0.1** | **0.20** |
| `arrive_gate_floor` | absent → gate ≡ 1.0 | **1.0** | **0.3** | **0.15** |
| `settle_speed_ref_mps` | absent → no speed gate | **1e6** | **0.4** | **0.25** |
| `w_near_goal_speed` | 0.1 | 0.1 | **0.3** | **0.5** |
| `w_action_rate` | 0.05 | 0.05 | **0.15** | **0.20** |
| `w_energy` | 0.01 | 0.01 | **0.02** | **0.02** |
| `w_position` / `w_heading` / `w_progress` / `w_cross_track` / `w_arrival` / `w_position_fine` / `pos_sigma_m` / `pos_sigma_fine_m` / `head_sigma_rad` / `xtrack_sigma_m` | — | copied | copied | copied |

`control` is the pre-R8 reward exactly, by construction: both new terms are off
(`w_hold = w_sat = 0`) and the arrival gate is a constant `1.0`. The gate is
`min(1, settle_speed_ref_mps / max(speed, eps))`, so any ref above the top speed keeps it at
1.0; `max_surge_mps = 1.0 m/s` in `configs/vehicle.yaml` is the soft cap and the vessel has
no way to pass it, so `1e6` is 1e6× margin and still exact in float32. This is stated in a
comment at the key in `env_control.yaml`.

**Caveat, stated plainly:** `settle_speed_ref_mps` / `arrive_gate_floor` / `w_hold` /
`hold_radius_m` do not exist in `envs/asv_env.py` on this branch yet (grep finds nothing).
The control arm is exact *if the landing `_reward` uses the gate form
`min(1, ref / max(speed, eps))` with the floor as the lower clamp and multiplies nothing by
`w_hold`/`w_sat` when they are 0*. If the landing formula differs (e.g. the floor also
scales the position kernel), re-check the control arm — that check belongs to whoever lands
the reward, not to these files.

## Commands to launch (PowerShell, from `E:\buoy-project\drl`)

Run from PowerShell in the repo root; the venv python is the only one with a working torch.

```powershell
# control
./.venv/Scripts/python.exe train.py --config configs/r8/train_control.yaml
# A
./.venv/Scripts/python.exe train.py --config configs/r8/train_A.yaml
# B
./.venv/Scripts/python.exe train.py --config configs/r8/train_B.yaml
```

To run the three side by side (each is one process; 10M steps each):

```powershell
Start-Process ./.venv/Scripts/python.exe -ArgumentList "train.py --config configs/r8/train_control.yaml" -RedirectStandardOutput runs/r8_control.log
Start-Process ./.venv/Scripts/python.exe -ArgumentList "train.py --config configs/r8/train_A.yaml"       -RedirectStandardOutput runs/r8_A.log
Start-Process ./.venv/Scripts/python.exe -ArgumentList "train.py --config configs/r8/train_B.yaml"       -RedirectStandardOutput runs/r8_B.log
```

Checkpoints land in `runs/r8_{control,A,B}/ckpt/ckpt_last.pt` (plus one every 2M steps);
TensorBoard logs in `runs/r8_{control,A,B}`.

### `train.py` flags used, and why nothing else is needed

Confirmed present in `train.py` (`argparse`, lines 372–386): `--config`, `--total-steps`,
`--iterations`, `--num-envs`, `--device`, `--seed`, `--log-dir`, `--ckpt-dir`, `--resume`,
`--curriculum-level`. Only `--config` is passed — every other value (10M steps, 2M save
interval, seed 0, `runs/r8_*`, `runs/r8_*/ckpt`) is already in the generated yaml, and the
flags override the yaml (`train.py:390`), so passing them again would just be a second
source of truth. `train.py:97` injects `curriculum.total_train_steps = total_steps`, so the
curriculum spreads over the 10M budget automatically.

### Evaluate after training

```powershell
# control
./.venv/Scripts/python.exe evaluate.py --ckpt runs/r8_control/ckpt/ckpt_last.pt --scenarios sk_wind,wp_square --episode-s 300 --dwell-stay-factor 1.0 --seeds 4 --out results_r8_control
# A
./.venv/Scripts/python.exe evaluate.py --ckpt runs/r8_A/ckpt/ckpt_last.pt --scenarios sk_wind,wp_square --episode-s 300 --dwell-stay-factor 1.0 --seeds 4 --out results_r8_A
# B
./.venv/Scripts/python.exe evaluate.py --ckpt runs/r8_B/ckpt/ckpt_last.pt --scenarios sk_wind,wp_square --episode-s 300 --dwell-stay-factor 1.0 --seeds 4 --out results_r8_B
```

Flags confirmed in `evaluate.py` `argparse` (lines 731–765): `--ckpt`, `--envs`,
`--episodes`, `--seeds`, `--seed`, `--scenarios`, `--rough-scale`, `--square-side`,
`--square-hold`, `--dwell-stay-factor`, `--episode-s`, `--dump-conditions`, `--plot-env`,
`--plot-seed`, `--device`, `--out`, `--no-plots`, `--tol`, `--hold-s`. Used above:
`--ckpt`, `--scenarios`, `--episode-s`, `--dwell-stay-factor`, `--seeds`, `--out` — all
exist, no invented flags.

Two things to know before reading the numbers (both from `evaluate.py` itself, not new):

- `--episode-s` is applied to **wp_square only** (help text, line 747–748); `sk_wind` keeps
  the 120 s of `SCENARIOS`. Passing it mutates the process-global `SCENARIOS` dict, so a
  mixed `--scenarios sk_wind,wp_square` run uses 300 s for whichever scenario object is
  built after the flag is applied — same call for all three arms, so the comparison stays
  fair, but the sk_wind episode length is not 120 s in such a run.
- `evaluate.py` loads `configs/env.yaml` directly (`env_cfg`, line 156–158) and has **no**
  CLI flag for the env config. An R8-trained policy is therefore evaluated in the pre-R8
  reward env. That is harmless for the metrics (reward is not scored by `evaluate.py`) but
  it means the new keys have no effect at eval time — and it also means eval is a fixed
  reference env for all three arms. If eval ever needs the R8 gates, `evaluate.py` must
  grow a flag; that is not this task's file.
